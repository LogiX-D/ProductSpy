## 本轮发现与修复

| 优先级 | 具体触发与影响                                                                                              | 修复与回归                                                                                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1     | 登录先读取并验证旧密码，再独立签发 session；期间改密已完成撤销，新 session 仍可逃逸撤销                     | 先查用户 ID，再取与改密相同的用户锁，锁内重读当前 hash、验证并签发。确定性真实 PostgreSQL 路由回归：旧码签发的 Cookie 在改密后访问 me 仍 200，修复后登录 401    |
| P1     | 改密事务完成 session 撤销、尚未处理授权码时，并发配对可消费旧码并签发未撤销扩展 token                       | 配对先识别 owner，再按“用户锁 → 事务 → 原子消费码 → 签发”顺序处理，避免反向锁顺序。真实 PostgreSQL 回归：旧 token 在改密后 bridge/status 仍 200，修复后配对 401 |
| P2     | 登录/注册仅在请求前广播；另一标签页可能在 Cookie 更新前重新取得旧账号，成功后没有通知使该缓存及在途响应失效 | Cookie 更新后再次清空并广播；双独立模块会话、共享 Cookie 的 3 项确定性回归在旧码均失败，修复后通过。现有页面会跳转登录，未据此声称已证明跨账号误写              |

注册的最终会话签发也在同一用户锁内重验密码。扩展授权码仍受来源绑定、有效期和单次消费约束；没有放宽认证或来源检查。

此前 PR 订阅流程复核已修复按小时 Checkout 幂等键、丢失响应重复结算及旧订阅事件覆盖新权益，详见 [验证记录](saas-validation.md)。支付回归是离线 provider/SDK 签名，不是实际 Stripe 交易。
